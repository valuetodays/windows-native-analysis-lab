# Demo Development Workflow v1.0

## 1. 定位

本文定义 Windows Native Analysis Lab 中 Demo 的标准开发流程。

目标：

保证每一个 Demo 不只是一个代码示例，而是一个完整的 Windows
用户态程序实验。

完整流程：

    实验设计

    ↓

    代码实现

    ↓

    编译生成

    ↓

    运行验证

    ↓

    x64dbg分析

    ↓

    实验报告沉淀

------------------------------------------------------------------------

# 2. Demo目录结构

标准结构：

    demos

    └── <领域>

        └── <Demo编号-名称>

            ├── README.md
            ├── main.cpp
            ├── build.bat
            └── analysis.md

示例：

    demos

    └── LIFE

        └── LIFE-001-process-start

            ├── README.md
            ├── main.cpp
            ├── build.bat
            └── analysis.md

------------------------------------------------------------------------

# 3. 开发顺序

## Step 1：编写 README.md

首先定义实验。

README 不是说明代码，而是实验设计。

需要明确：

-   实验目标
-   背景知识
-   涉及 Windows 能力
-   涉及 API
-   观察目标
-   预期结果

示例：

    实验目标：

    观察 Windows 用户态程序启动流程。

    验证：

    - PE EntryPoint
    - Module加载
    - main调用
    - Process Exit

------------------------------------------------------------------------

## Step 2：编写实验程序

根据 README 中定义的目标，实现最小程序。

原则：

-   代码最少
-   行为明确
-   易于调试
-   易于观察

避免：

-   一个 Demo 包含多个无关功能
-   为了展示代码而增加复杂逻辑

目标：

    一个知识点

    ↓

    一个最小实验

------------------------------------------------------------------------

## Step 3：编写编译脚本

每个 Demo 应包含独立编译方式。

例如：

    build.bat

负责：

-   固定编译参数
-   生成 exe
-   保证实验可重复

推荐：

    -g

    -O0

    -Wall

原因：

-   保留调试信息
-   避免优化影响分析
-   提高代码可观察性

------------------------------------------------------------------------

## Step 4：运行验证

确认：

-   程序可以启动
-   行为符合预期
-   没有编译环境问题

验证：

    source

    ↓

    compile

    ↓

    exe

    ↓

    run

------------------------------------------------------------------------

## Step 5：x64dbg分析

进入动态分析阶段。

观察：

## 程序入口

例如：

-   EntryPoint
-   main

## API调用

例如：

-   kernel32.dll
-   user32.dll

## 运行状态

观察：

-   Registers
-   Stack
-   Memory
-   Modules
-   Threads

目标：

理解：

    程序行为

    ↓

    Windows API

    ↓

    系统机制

------------------------------------------------------------------------

## Step 6：填写 analysis.md

记录实验结果。

包括：

-   实验环境
-   PE信息
-   断点位置
-   调用流程
-   参数变化
-   内存变化
-   异常信息
-   最终结论

analysis.md 是实验知识沉淀。

------------------------------------------------------------------------

# 4. Git提交流程

推荐：

## 开发阶段

在：

    dev

分支开发。

提交可以比较细：

    add initial demo structure

    implement basic logic

    fix build script

    update analysis notes

------------------------------------------------------------------------

## 合并阶段

完成实验后：

使用：

    Squash and Merge

合并到：

    main

保持 main 历史清晰。

main:

    Initial project structure

    Add documentation

    Add LIFE-001 demo

    Add PROC-001 demo

------------------------------------------------------------------------

# 5. Demo完成标准

一个 Demo 完成，需要满足：

-   README 完成
-   程序运行成功
-   编译流程固定
-   x64dbg分析完成
-   analysis.md完成
-   关联 Knowledge Map

------------------------------------------------------------------------

# 6. 核心原则

## 先设计，再编码

不要：

    写代码

    ↓

    看看发生什么

而应该：

    定义想观察什么

    ↓

    设计最小程序

    ↓

    验证行为

------------------------------------------------------------------------

## 先观察，再深入

学习目标不是记忆 API。

目标：

看到程序行为时：

    知道可能涉及什么 Windows 能力

    知道如何验证

    知道如何分析

------------------------------------------------------------------------
